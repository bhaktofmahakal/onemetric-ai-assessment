# Repository Guidelines

## Purpose and Architecture

This Next.js App Router project combines a deterministic RevOps evaluator with an optional TypeSafe System One decision layer and a bounded, webhook-driven agent runtime. Dashboard scenarios and custom-event dispatch use `demo-store.ts`; live domain evaluation at `/api/engine/evaluate` requires HubSpot schema and Upstash Redis, then runs exactly one `runIntentAgentCycle`. Production event ingestion starts at `/api/engine/webhook`; normalized Bombora and G2 adapters are available under `/api/engine/webhook/{bombora,g2}`. These provider adapters require the shared raw-body HMAC contract and are not direct provider subscription integrations. Redis is accessed through its HTTPS REST interface in `persistent-agent-store.ts`; in-memory module state is not used for production agent memory.

The agent’s objective is fixed: evaluate one account event, synchronize contact dispositions, create a consolidated AE task when escalated, and stop for completion or human review. TypeSafe may choose only among currently available tools: `sync_contacts`, `create_ae_task`, `request_human_review`, and `complete`. `complete` is available only after required CRM writes succeed. Both human-review and AE-task tools create a consolidated HubSpot task; review status is recorded separately. TypeSafe uses `POST https://api.typesafe.ai/v1/systemone`, model `jev-latest`, and a `next_tool` Choice with criteria built from the available-tool set. If TypeSafe is unconfigured or fails, Gemini is called with a JSON schema constraining `tool` to the available tools and a numeric confidence. Gemini tries the configured model, configured fallback model, then `gemini-2.5-flash`, `gemini-2.0-flash`, and `gemini-flash-lite-latest`, without duplicate model names; HTTP 429, 503, and 404 advance to the next model. Confidence below `0.65` requests human review. Model responses are parsed and checked against available tools; neither model can bypass FSM guards. In production, if both live planners fail, the session fails and persists the error; only local development may use the deterministic tool planner.

## Decision Model

`scoring.ts` owns defaults and pure score math. For signal age `t` days, source weight `w`, raw score `r`, and half-life `h=14`, a contribution is `r × w × exp(-ln(2) × t / h)`. Invalid, future, older-than-30-day, out-of-range, and decayed-under-10 signals are excluded. Same-source passive visits to the same page on the same UTC day are dampened to `sum(scores) × ln(1+n) / n`. Remaining contributions sum, cap at 35 if fewer than two source types are represented, then cap at 100. Switch hysteresis requires both `competingScore - currentScore >= 25` and `competingScore >= 50`.

Live HubSpot contact reads require readable contact properties `current_campaign` (string) and `touch_count_7d` (number). `scripts/ensure-hubspot-contact-properties.mjs` checks these definitions and creates only missing definitions; its token needs the `crm.schemas.contacts.write` scope. A missing or invalid per-contact touch count is mapped to `fatigueMaxTouches`, which fails closed and blocks automated campaign touches. This field must be maintained by a connected channel activity source; a newly created empty property is not a real rolling-window counter. The webhook readiness route checks that both definitions are readable before reporting ready. `/api/engine/evaluate` and `/api/engine/committee` check the schema before starting live evaluation and return HTTP 424 with `HUBSPOT_CONTACT_SCHEMA_INCOMPLETE` and a `missingProperties` list; they stop before CRM writes. Demo scenario dispatch remains separate.

FSM guard order matters: terminal `EXITED`; exit signal; high-intent multi-product conflict; Tier-1/2 active-deal escalation when the dual gate passes; contact fatigue; persona; cross-BU; cooldown cadence. Deal/conflict handoffs outrank fatigue because a review task is not a campaign touch. Fatigue pauses at two touches in seven days or when the last touch is less than 72 hours ago (invalid/future touch dates fail closed). A sustained dual-gate shift enters `EVALUATION_COOLDOWN` for 48 hours. At recheck, a still-valid gate and persona match moves to `SWITCHING` within the same BU or `ESCALATED` across BUs; a decayed signal returns to `ACTIVE_CURRENT`. Moderate unmet shifts enter `MONITORING`; weak shifts continue. `fsm.ts` is authoritative for state transitions; Jev scores and tool selection do not bypass its guards.

## Persistent State and Feedback

Redis stores account memory (last 200 intent events, per-contact FSM/campaign/cooldown state, source weights, recent feedback), session journals, due-work sorted sets, dedupe claims, locks, and rate counters. Event IDs are retained for 90 days after session creation; in-progress claims expire after 10 minutes. Feedback IDs are claimed for 90 days. Locks use `SET NX EX` and compare-before-delete. Cooldowns are scheduled at 48 hours; `vercel.json` invokes the GET worker daily, so rechecks can be late by up to a day. Failed tools retry three times in-cycle, then wait five minutes; worker retries use `min(60, 5 × 2^min(attempts−3, 4))` minutes and stop after eight attempts.

The signed feedback route applies fixed deltas to the event’s source weight: open `+0.01`, reply `+0.05`, meeting/won `+0.08`, lost `−0.05`, unsubscribe `−0.08`, clamped to `[0.1, 1.0]`. Updated weights affect future evaluations for that account. This is a heuristic, not model training. Intent and feedback requests require raw-body HMAC-SHA256 in production; Redis fixed-window limits are 60 intent requests/IP/minute and 30 feedback requests/IP/minute.

The browser dashboard does not POST to `/api/engine/feedback`. Feedback is a server-to-server integration: every request must have `x-onemetric-signature: sha256=<HMAC-SHA256 of the exact raw JSON body>`, a unique `feedbackId`, domain, product, event type, and source type. The route rejects unsigned requests, requires Redis, applies a Redis rate limit, claims feedback IDs for 90 days, and updates only durable account memory. It never bypasses authentication based on caller-provided body fields or headers and never reports demo-store mutation as persisted feedback. Optional `mode: "bayesian"` uses the explicit calibration formula in `scoring.ts`; the default remains the documented bounded fixed-delta heuristic.

`src/engine/product-catalog.ts` is the sole live product allowlist. Intent, Bombora, G2, and feedback routes reject unknown products; an unmapped Bombora topic is rejected rather than silently assigned to Product A. Live committee scoring never invents a prior email-click event from `lastTouchDate`. `checkSmartCooldown` and `checkCooldownActive` use the FSM's injected clock so scenario evaluation is reproducible.

Campaign execution is currently disconnected. `batchSyncContacts` does not write fake values such as `cooldown_product_a` or `suppressed_fatigue` into `current_campaign`; it returns a human-review requirement for any switch, pause, or suppression action. The account memory retains the CRM-observed campaign until a real enrollment is confirmed. `syncToHubSpot` is a disabled legacy path and makes no HTTP calls. Scenario/demo dispatch never writes to a live HubSpot contact. The webhook readiness response checks Redis with `PING` and exposes `campaignEnrollment: not_connected` and `rollingTouchCounter: not_connected` even when the decision agent itself is ready.

HubSpot Sequences API access must use an app configured for user-level OAuth; account-level apps/private-app tokens are not supported by the current Sequences API guide. Enrollment needs the relevant sequence scopes, an assigned Sales/Service Professional or Enterprise seat, an accessible sequence, and a connected sender inbox. The tenant currently has zero sequences for the checked user, no enabled relevant workflow, and no authoritative outbound touch feed. Do not treat HubSpot workflow API access as evidence that a sequence is enrolled or that email has been sent.

## Commands and Configuration

- `npm run dev` starts the local dashboard.
- `npm run typecheck` runs strict TypeScript checking (`tsconfig.json`).
- `npm run test:engine` runs the scenario CLI in `src/test-engine.ts`.
- `npm run smoke:gemini` performs one real constrained Gemini planner call using `.env.local`; it makes no CRM writes.
- `npm run smoke:typesafe` performs one live TypeSafe Jev decision against a fixture state and makes no CRM or Redis writes.
- `npm run smoke:agent-planners` calls the actual TypeSafe tool-choice function and Gemini planner function using one allowed tool; it makes no CRM, Redis, or campaign writes.
- `npm run smoke:redis` sends a read-only `PING` to Upstash Redis and never writes a test key.
- `node scripts/smoke-hubspot-read.mjs` performs a read-only GET for the supplied smoke contact ID (defaults to the previously provided contact); it prints property presence and touch-counter population only, never contact PII or credentials.
- `node scripts/inspect-hubspot-touch-sources.mjs` performs read-only workflow, sequence, owner, and contact activity association queries; it prints workflow/sequence names and IDs plus aggregate activity counts, never secrets or contact PII.
- `npm run smoke:production` performs read-only GET checks against the production deployment (override with `PRODUCTION_BASE_URL`). It reports readiness blockers without submitting CRM events.
- `npm run build` compiles the Next.js production app.

Use `.env.example` for variable names. Production requires `INTENT_WEBHOOK_SECRET`, `OUTCOME_WEBHOOK_SECRET`, `CRON_SECRET`, `HUBSPOT_ACCESS_TOKEN`, and `UPSTASH_REDIS_REST_URL` plus `UPSTASH_REDIS_REST_TOKEN`, readable custom contact schema, and at least one live planner key (`TYPESAFE_API_KEY` or `GEMINI_API_KEY`). `TYPESAFE_API_KEY` enables the preferred typed tool choice; Gemini is the live structured-output fallback. The webhook readiness GET verifies both HubSpot custom property definitions and planner configuration. Keep actual credentials in ignored `.env.local` or deployment secret settings; never commit them or paste them into docs.

Production verification is time-sensitive; confirm the current deployment with `npm run smoke:production` before reporting readiness. A configured schema GET verifies property definitions, not that `touch_count_7d` is maintained from every outbound channel. Bombora and G2 routes are normalized adapters behind OneMetric HMAC, not vendor-authenticated subscriptions. The dashboard's live domain evaluation now runs one durable agent cycle and projects its result for display; simulations continue to use demo state. Do not claim an end-to-end CRM write or live planner call unless that specific run was observed and recorded.

## Change Boundaries

Keep scoring formulas and thresholds in `scoring.ts`, state transitions in `fsm.ts`, TypeSafe request/response decoding in `jev-agent.ts`, and tool availability/execution in `agent-runtime.ts`. Update this file when changing a threshold, transition, tool contract, persistence key/TTL, retry policy, or external credential requirement. HubSpot and TypeSafe behavior must be represented by observed responses; do not add simulated success IDs or report demo-store results as live writes. There is no repository Git history or separate architecture-doc directory to rely on; this guide and the source are the current record.
